附录 1

GasUsed 计算

区分 intrinsic gas、正常执行结算以及 calldata/access-list 最低地板。

Gas 计量

一、总公式

intrinsic_gas = B + 4Z + 16N + access_list_access_cost + access_list_data_cost + authorization_cost + initcode_word_cost
正常账单（refund 前）= intrinsic_gas + X
正常 gasUsed = 正常账单 - refund

最低地板 = B + 64 × (Z + N) + access_list_data_cost
最终 gasUsed = max(正常 gasUsed, 最低地板)

intrinsic_gas 是不读取链上状态即可根据交易字段确定的最低执行前成本；有效交易在进入 EVM 前先从 gas budget 中扣除它。X 是随后实际发生的 pre-execution runtime、EVM opcode、state gas、initcode 执行和代码存储等消耗。最终 gasUsed 用于交易收据与手续费结算。

创建成本的位置：EIP-2780 生效后，顶层 contract-creation transaction 的固定创建访问成本已经包含在 B 中，不再额外叠加旧规则的 32,000 gas。只有创建交易才有的 initcode_word_cost 仍单独属于 intrinsic gas。

二、符号含义

B：交易基础形状成本
12,000 + recipient_component + value_component。它是正常账单与最低地板共有的 base，不等于“全部 intrinsic gas 减去 calldata”。
Z / N：calldata 字节数
Z 为零字节数量，N 为非零字节数量。标准 intrinsic 成本为 4Z + 16N，EIP-7976 floor 为统一的 64 × (Z + N)。
A / K：Access List 条目数
A 为 address 数量，K 为 storage key 数量；两者同时产生状态访问预付费和 EIP-7981 数据体积费。
H：authorization 数量
EIP-7702 authorization tuple 的数量。每个 tuple 的固定 intrinsic 成本都会收费，不取决于它后续是否通过状态相关检查。
X：实际 runtime 消耗
包含 pre-execution runtime charge、普通 EVM 执行、state gas、initcode 执行及 runtime code deposit；只对实际发生的工作收费。
refund：最终退款
按 EIP-3529 受 refund counter 和已用 gas 的 1/5 上限约束；应用 refund 后，最终收费仍不能低于最低地板。

三、B 的计算

B = TX_BASE_COST 12,000 + recipient_component + value_component
  • self-transfer：recipient_component = 0，非零 value 也不额外收费，所以 B = 12,000。
  • 普通目标地址：recipient_component = COLD_ACCOUNT_ACCESS = 3,000；若向不同地址转移非零 ETH，再加 TX_VALUE_COST = 6,000，因此零 value 为 15,000，非零 value 为 21,000。
  • 顶层创建交易：recipient_component = CREATE_ACCESS = 12,000，不因 tx.value 再收费，因此 B = 24,000。

Authorization、access list、initcode word 与依赖链上状态的 runtime charge 均不属于 B。

四、Access List 成本

在完整 Glamsterdam 组合中，EIP-8038 先调整状态访问预付费，EIP-7981 再按数据体积叠加 64 gas/byte：

access_list_access_cost = 2,900A + 2,000K
access_list_data_cost = 1,280A + 2,048K = 64 × (20A + 32K)

access_list 总 intrinsic 成本 = 4,180A + 4,048K

其中 access_list_access_cost 为账户/storage slot 的状态访问和预热付费；access_list_data_cost 为 address 的 20 bytes 与 storage key 的 32 bytes 支付区块数据成本。后者同时出现在正常账单和最低地板中，不能再被用于绕过 calldata floor。

若只孤立看 EIP-7981、尚未叠加 EIP-8038，则原状态访问基线是 address 2,400、storage key 1,900；本文按 Glamsterdam 最终组合参数使用 2,900/2,000。

五、Authorization 成本

authorization_cost = 7,816 × H execution gas

7,816 是每个 EIP-7702 authorization 的 state-independent intrinsic 成本，覆盖 tuple 数据、authority 签名恢复、固定 cold authority access 和基础 warm writes。它替代旧 EIP-7702 每项预留 25,000 gas、随后可能退款的模型。

通过状态检查的 authorization 还可能在 runtime 阶段产生以下费用，这些费用计入 X，而不是 intrinsic gas：

  • authority 在本交易中的第一次未覆盖写入：ACCOUNT_WRITE = 9,000 execution gas。
  • authority 账户原本不存在：120 × 1,530 = 183,600 state gas。
  • 首次新增 23-byte delegation indicator：23 × 1,530 = 35,190 state gas。

六、Contract Creation 与 Initcode

顶层创建交易的 B = 12,000 + 12,000 = 24,000 execution gas
initcode_word_cost = 2 × ceil(initcode_length / 32) execution gas
  • Initcode 本身：创建交易的 tx.data 就是 initcode，因此仍按 4Z + 16N 计入正常 intrinsic，并按 64 × (Z + N) 参与 EIP-7976 floor。
  • 新 deployment account：目标地址不存在时，在 runtime 阶段收取 120 × 1,530 = 183,600 state gas；目标已有 state leaf 时不收。
  • 执行 initcode：构造函数执行消耗计入 X，不是固定 intrinsic 成本。
  • 存储 runtime code：Amsterdam 下收取 6 × ceil(runtime_code_length / 32) execution gas 作为 hash 成本，并收取 1,530 × runtime_code_length state gas 作为 code deposit。
  • 内部 CREATE/CREATE2：固定创建访问成本为 12,000 execution gas；两者都加 2 gas/word initcode 分析费，CREATE2 还加 6 gas/word 地址哈希费，其余新账户与代码存储费用与上面相同。

七、有效性与最终结算

交易有效性要求：tx.gasLimit ≥ max(intrinsic_gas, 最低地板)
正常 gasUsed = gasUsedBeforeRefund - refund
最终 gasUsed = max(正常 gasUsed, 最低地板)
实际手续费 = 最终 gasUsed × effectiveGasPrice

一笔已被接受的交易即使随后 REVERT 或执行失败，intrinsic gas 仍然已经消耗；未使用的 runtime gas 会返还。EIP-7778 对区块 gas 容量采用不扣 refund 的口径，与这里用于 receipt 和手续费的最终标量 gasUsed 是不同层面的记账。

八、effectiveGasPrice

effectiveGasPrice 是交易被区块包含后，用户实际为每单位 execution/state gas 支付的价格。对 EIP-1559 动态费用交易：

effectiveGasPrice = min(
  maxFeePerGas,
  block.baseFeePerGas + maxPriorityFeePerGas
)

交易在当前区块可被包含，至少需要满足：

maxFeePerGas ≥ block.baseFeePerGas
maxFeePerGas ≥ maxPriorityFeePerGas

否则交易当前不能被该区块包含，需要等待 base fee 降低，或者通过 replacement transaction 提高费用上限。

baseFeePerGas
当前区块规定的基础费用，由协议根据上一个区块的拥塞程度计算，用户不能指定，最终被 burn。
maxPriorityFeePerGas
用户愿意支付给 proposer 的最高小费；实际小费还会受到 maxFeePerGas - baseFeePerGas 的限制。
maxFeePerGas
用户愿意支付的总 gas 单价上限，包含 base fee 和 priority fee；它是价格上限，不是必然支付的价格。
实际 priorityFeePerGas = effectiveGasPrice - block.baseFeePerGas

Burn = gasUsed × block.baseFeePerGas
Proposer 收入 = gasUsed × 实际 priorityFeePerGas
